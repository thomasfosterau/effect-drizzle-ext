## Hooks

- The SessionStart hook (`.claude/hooks/session-start.sh`) installs the global Vite+ CLI at the catalog's `vite-plus` pin with the official installer (npm-provenance and SHA-512 checked; it needs `vite.plus` and `viteplus.dev` on the environment's allowlist), links `vp` and `vpx` into `~/.local/bin` (the CLI lives under `$VP_HOME` when set, as in the Vite+ container image, else `~/.local/share/vite-plus`), and installs dependencies against the lockfile with `vp install --frozen-lockfile`. It removes the `fallow` / `tsx` entries and the walking `vp` shim earlier versions put there. Everything else goes through Vite+: `vp exec fallow …` for fallow, `vpx <file>.ts` for scripts (`tsx` is installed only because `@effect/docgen` requires it as a peer and runs it itself). If the installer can't run, `vp` falls back to this checkout's `node_modules` copy. It hydrates no secrets; none are needed. The global `vp` delegates to each checkout's own `vite-plus`, so a worktree needs its own `pnpm install` before `vp` runs in it; without one, `describe()` throws `Cannot read properties of undefined (reading 'config')`.
- A PreToolUse hook (`.claude/hooks/fallow-gate.sh`, generated by `fallow hooks install --target agent --agent claude` with marked local edits for the base, the audit directory, trusted checkouts, how it reports a skipped audit and the one-line version (effect-drizzle-ext#73), all re-applied by hand after a `fallow hooks install --force`) blocks `git commit` / `git push`, including with git global options such as `git -C dir commit` or `git --no-pager push`, when `fallow audit` against the default branch (`FALLOW_AUDIT_BASE` if set, else `origin/HEAD` when it resolves, else `origin/trunk`) returns `fail`. When no base ref resolves locally it blocks too, naming the fix: `git fetch origin trunk:refs/remotes/origin/trunk`, `git remote set-head origin --auto` for a stale `origin/HEAD`, or a `FALLOW_AUDIT_BASE` that exists (effect-drizzle-ext#61). The exception is a checkout with no `origin` remote (a scratch `git init` repo), which has nothing to fetch: there it skips the audit with a notice, wherever the base is resolved (the directory Claude Code runs it in, a `cd` / `-C` target, or either half of a both-audits run). That exception doesn't cover this project: a checkout that shares its git directory (`git rev-parse --path-format=absolute --git-common-dir` equal to the one in `$CLAUDE_PROJECT_DIR`, so the primary checkout and its worktrees) still blocks after its `origin` is renamed or removed, and names `git remote add origin …` or a `FALLOW_AUDIT_BASE` set in Claude Code's environment as the fix (effect-drizzle-ext#71). `FALLOW_AUDIT_BASE` is read from the hook's environment, which is Claude Code's, so set it there (exported before Claude Code starts); a `FALLOW_AUDIT_BASE=… git commit` prefix on the command doesn't reach the hook. It fails open on a runtime error (jq or fallow missing, fallow's own error JSON, an unexpected exit code) or outside a git checkout, and every fail-open or fallback notice reaches both the user (`systemMessage`) and the agent (`additionalContext`) as hook JSON; a passing audit and a command that isn't a `git commit` / `git push` print nothing, except without jq: the hook can't parse the command then, so any Bash call whose hook input (the command, its description, the cwd, the transcript path) contains `commit` or `push` (`echo push`, or `git log` described as "Show recent commits", included) prints the jq-missing notice. A notice means the write went through without a full audit, so run the audit yourself in the checkout it targets (see [Verification](#verification)). It audits the checkout the command targets (effect-drizzle-ext#58). For the one shape it models (leading `cd <dir>` segments, then plain `git` commands, then the `git commit` / `git push` with any `-C <dir>`, joined by `&&`, `;` or newlines) it audits only the top level of that target, so `cd .claude/worktrees/<name> && git commit` or `git -C .claude/worktrees/<name> commit` run from the primary checkout is gated on the worktree's changes alone. When that target is another checkout and the command has anything else (a subshell, `||`, a pipe, a lone `&`, a heredoc, `$` or a backtick, a backslash, a comment, a separator inside quotes, `pushd` / `popd`, a `GIT_*` variable, `--git-dir`, `--work-tree` or `-c`, a `cd` with several operands, another command before the write, or a `cd` or differently targeted write after it), it audits both the target and the directory Claude Code runs it in and blocks if either fails. With such a target, a `GIT_DIR` / `GIT_WORK_TREE` in the hook's environment also triggers both audits, as does any `(`, `)` or `$` in a quoted message, so `cd <worktree> && git commit -m "feat(core): …"` or one with a `-m "$(cat <<'EOF' …)"` message gets both. A target it can't follow (`cd -`, a `$VAR`, `~user`, `~` with `HOME` unset, a `cd` option other than `-L` / `-P`, or an `-L` after a `-P`) or one that isn't a directory inside a git checkout falls back to the directory Claude Code runs it in, with a notice, so step 9 of [Verification](#verification) in the worktree stays the real check. It runs a checkout's tooling only in this project and its `.claude/worktrees/<name>` checkouts (judged on the checkout's top level, so a commit from a subdirectory is still audited, and neither a repository nested inside a worktree nor a separate clone placed at a worktree path, which shares no git directory with this project, is trusted): there fallow runs as `vp exec fallow` (the checkout's own pinned copy; its `node_modules/.bin/fallow` without `vp` on PATH), and a commit or push whose target is any other tree is skipped with a notice (or, for a command it doesn't model, only the directory Claude Code runs it in is audited), so a scratch clone's `node_modules` never runs.
- A PostToolUse hook runs `vp fmt` on every source, JSON, CSS or Markdown file you write or edit.

## Worktrees

- Agent work uses git worktrees under `.claude/worktrees/`, one per branch, named `issue-<n>-<slug>` for issue-linked work. Start every command that targets a worktree with an explicit `cd` and confirm with `git log -1` before committing.

## What can't run in a session

- Won't run in an agent session: `vp run test:integration`, which needs a Docker daemon or a reachable PostgreSQL server. A cloud session normally has neither, so its global setup fails. Say so in the PR body and rely on CI, which runs it against a `pgvector/pgvector:pg17` service container. Every other gate runs offline. A session that can install PostgreSQL (for example `service postgresql start` with a `postgres` password, then `PGHOST=localhost PGUSER=postgres PGPASSWORD=postgres`) can run the suite against it through the `PG*` path of `provisionTestDatabase`.
